    10→# 1. Mission and governing principles
    11→
    12→Build PlayLiquid as a game creation, discovery, playback, social and publishing platform on top of the existing ZCode codebase.
    13→
    14→The objective is NOT to build another AI coding application, game launcher or generic game dashboard.
    15→
    16→The objective is to take the existing ZCode application and extend it into PlayLiquid while retaining the capabilities that already make ZCode useful.
    17→
    18→The team must follow five non-negotiable rules:
    19→
    20→1. **Do not rebuild existing ZCode features.** Preserve the existing implementation and extend it only where necessary.
    21→2. **Do not replace ZCode's existing settings page.** Its model/provider configuration capabilities are particularly important and must remain functional.
    22→3. **Reuse WebFlix's existing UI/UX implementation wherever code reuse is permitted and technically practical.** Do not independently reinvent existing navigation, feed, card, watch-page, Shorts and Creator Studio patterns.
    23→4. **Reproduce the approved Figma designs.** The TL and workers must implement the actual screens and layouts, not invent their own interpretation of PlayLiquid.
    24→5. **Game-specific capabilities must integrate with the existing ZCode architecture.** Do not introduce another agent runtime, model-provider framework, settings system or unnecessary backend.
    25→
    26→The product should feel like PlayLiquid, not like ZCode with a different logo. However, its underlying ZCode capabilities must remain available.
    27→

   300→# 6. The game-thumbnail and hover-to-play experience
   301→
   302→This feature is a major product requirement.
   303→
   304→WebFlix's video cards do not merely display static thumbnails. When the user hovers over a card, the thumbnail becomes a video-preview surface and plays the content inside the card.
   305→
   306→PlayLiquid needs the same experience for games.
   307→
   308→The implementation must not be a decorative zoom, animated slideshow or rotating collection of screenshots pretending to be video playback.
   309→
   310→## 6.1 Game card presentation
   311→
   312→Every game should have a proper thumbnail and preview asset.
   313→
   314→The card must support:
   315→
   316→- Game thumbnail/poster.
   317→- Game title.
   318→- Creator/developer identity.
   319→- Plays and other relevant game metadata.
   320→- Game duration or estimated play time where applicable.
   321→- Continue-playing progress where relevant.
   322→- Game status, such as live, upcoming or recently updated.
   323→- A real gameplay preview on hover.
   324→
   325→Long-form game cards should use landscape presentation.
   326→
   327→Sparks should use vertical 9:16 presentation.
   328→
   329→The same reusable card and preview components should be used across Home, recommendations, search, subscriptions, game details and other relevant feed surfaces.
   330→
   331→## 6.2 How the hover preview should work
   332→
   333→Start by studying the existing WebFlix implementation:
   334→
   335→`src/components/video/video-hover-preview.tsx`
   336→
   337→Its existing architecture is especially relevant:
   338→
   339→- A shared preview layer follows the currently hovered card.
   340→- A short hover dwell prevents accidental playback.
   341→- Only one preview player is active at a time.
   342→- The preview is muted by default.
   343→- Preview controls provide mute and timeline/scrubbing behavior.
   344→- Leaving the card stops and cleans up the preview.
   345→- The preview uses the card's actual geometry.
   346→- Touch devices do not attempt to use hover.
   347→- Failed playback falls back honestly to the static thumbnail.
   348→
   349→The implementation should reuse this architecture where possible, changing the video entity and media source to PlayLiquid's game-preview assets.
   350→
   351→Use a tunable initial hover dwell around 450–600 ms, then optimize through real user testing.
   352→
   353→The preview should:
   354→
   355→1. Display the static game thumbnail immediately.
   356→2. Wait until the pointer has remained over the card for the dwell interval.
   357→3. Load and play the associated gameplay-preview video inside the card.
   358→4. Start muted and inline.
   359→5. Display appropriate preview controls, including mute and progress.
   360→6. Stop playback and release resources when the user leaves the card.
   361→7. Keep the card clickable so that selecting it opens the game page.
   362→8. Ensure that moving between the card and its preview controls does not accidentally close the preview.
   363→
   364→Only one global preview player should normally be active at a time. Do not create dozens of independent players for every visible card.
   365→
   366→## 6.3 Do not launch the full game engine just to preview a card
   367→
   368→This is an important architectural distinction.
   369→
   370→Hovering over a game card should play a lightweight video asset captured from actual gameplay. It should not boot a full game engine, download a large game bundle or create a live game session for every hover.
   371→
   372→That would create unnecessary startup latency, CPU/GPU use, network consumption and memory pressure.
   373→
   374→The game preview is a media asset, not a complete game execution.
   375→
   376→Actual interactive gameplay should be started through an explicit Play or Try action.
   377→
   378→## 6.4 Preview asset generation
   379→
   380→Build a reusable game-preview asset pipeline.
   381→
   382→Each game should be able to provide:
   383→
   384→- A manually uploaded thumbnail.
   385→- A manually uploaded gameplay-preview video.
   386→- An automatically captured gameplay-preview video.
   387→- A fallback poster generated from a valid game frame.
   388→- Preview orientation and aspect ratio.
   389→- Preview duration and media metadata.
   390→- Source build/version information.
   391→
   392→A sensible first implementation is:
   393→
   394→1. The creator publishes or selects a build.
   395→2. The creator opens a preview-capture workflow.
   396→3. A controlled capture session starts the selected game build.
   397→4. The capture process records a short, representative gameplay sequence.
   398→5. The capture produces a thumbnail and compressed preview clip.
   399→6. The creator reviews and approves the generated assets.
   400→7. The assets are stored and referenced by the game's metadata.
   401→8. The game card uses those assets for its hover preview.
   402→
   403→The creator must be able to replace the automatic capture with a manually uploaded or recorded preview.
   404→
   405→Use an asset/media delivery layer that supports efficient playback, caching and appropriate resolutions.
   406→
   407→Start with a widely supported browser video format and add additional encodings only when justified by measured compatibility and performance.
   408→
   409→## 6.5 Honest fallback behavior
   410→
   411→The preview must never silently degrade into a slideshow that looks like a playing video.
   412→
   413→If playback is still loading, retain the static thumbnail.
   414→
   415→If playback fails, stop attempting playback, display the static poster and optionally show a small "Preview unavailable" indicator.
   416→
   417→Do not animate storyboard images as a substitute for a real video preview on video-capable devices.
   418→
   419→Browsers may block autoplay of audible media. Use muted inline previews and handle rejected playback promises gracefully. See the browser autoplay guidance:
   420→
   421→https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay
   422→
   423→For users who prefer reduced motion, do not force autoplay. For touch devices, provide an explicit preview or play interaction rather than relying on hover.
